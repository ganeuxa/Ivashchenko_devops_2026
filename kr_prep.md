# Подготовка к КР №4

## 1. Когда я выберу rebase, а когда merge? Почему?

Rebase беру для своей ветки, которую ещё никто кроме меня не скачивал. Например, делаю `feature/login`, а в main за это время влили чужие коммиты. Делаю `git rebase main`, и мои коммиты встают поверх свежего main без лишнего merge-коммита. Перед PR ещё прохожусь `git rebase -i` и склеиваю «wip» и «fix typo» с нормальными коммитами.

Merge беру, когда вливаю в общую ветку, например готовую фичу в main. Он не трогает уже существующие коммиты, так что у остальных ничего не сломается, а по графу потом видно, что фича шла отдельной веткой.

## 2. Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?

Rebase заново создаёт все перенесённые коммиты, у них будут новые хеши. Обычный push такое не примет, придётся делать `git push --force`. У коллег в локальной копии останутся старые коммиты, и при следующем `git pull` Git попробует слить старую и новую версию одних и тех же изменений. Получатся дубли и конфликты. А если кто-то успел запушить свою работу поверх старой истории, мой force push её просто сотрёт с сервера.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?

Чтобы один локальный репозиторий мог отправлять и забирать код из нескольких мест. Я так делал в практической №3: `origin` на GitHub и зеркало `mirror`, и `git push origin` отправляет в оба сразу.

Где это нужно в реальной работе:

- бэкап на второй площадке, например копия на GitLab или на сервере компании, если GitHub недоступен;
- работа с форком: `origin` это мой форк, `upstream` это оригинальный проект, из него я подтягиваю обновления;
- деплой пушем в отдельный remote, так работают Heroku и Dokku;
- переезд с одной платформы на другую без потери истории, через `git push new --all` и `git push new --tags`.
