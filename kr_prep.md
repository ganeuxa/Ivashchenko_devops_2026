# Подготовка к КР №4

## 1. Когда я выберу rebase, а когда merge? Почему?

**Rebase** — для своей локальной feature-ветки, которую ещё никто не забрал: перед PR подтягиваю свежий main через `git rebase main`, а через `git rebase -i` склеиваю рабочие коммиты («wip», «fix typo») в осмысленные. История получается линейной и читаемой.

**Merge** — для общих веток, с которыми уже работают другие (влить фичу в main, влить main в долгоживущую общую ветку). Merge не переписывает существующие коммиты, поэтому безопасен и честно показывает, что работа шла параллельно.

## 2. Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?

Rebase создаёт новые коммиты с новыми хешами вместо старых. Чтобы отправить это на сервер, придётся делать `git push --force`, и у коллег их локальная ветка разойдётся с удалённой: при следующем `pull` Git попытается слить старые и новые версии тех же коммитов — появятся дубли и конфликты, а если кто-то успел запушить свою работу поверх старой истории, force push её просто затрёт. Поэтому золотое правило: never rebase public branches.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?

Multi-remote позволяет одному локальному репозиторию работать с несколькими удалёнными. Сценарии:

- **Зеркало/бэкап** — основной репо на GitHub, копия на GitLab или внутреннем сервере компании на случай недоступности или блокировки сервиса.
- **Forking workflow** — `origin` смотрит на свой форк, `upstream` — на оригинальный репозиторий проекта, чтобы подтягивать из него обновления и отправлять PR.
- **Разные среды/команды** — например, код хранится на GitHub, а деплой идёт пушем в отдельный remote (Heroku, Dokku, внутренний GitLab с CI).
- **Миграция** между платформами без потери истории (`git push new-remote --all --tags`).
